How we apply the CHAOSS metrics

Where a project's datasets, models or code live on GitHub, Hugging Face or Zenodo, we read their public activity once a week and report it with the metrics of CHAOSS, the Linux Foundation's Community Health Analytics in Open Source Software project. We report facts, not scores.

What CHAOSS is

CHAOSS (Community Health Analytics in Open Source Software) is a Linux Foundation project that defines how to measure the health of open-source communities. We use its metric definitions, not its software, and adapt them where a catalogue of datasets and models needs it. CHAOSS does not review or endorse this catalogue.

Which links we read

We read each project's dataset links and its use-case, model and app links; additional resources and hosted documents are not measured. Every GitHub repository, Hugging Face model, dataset or space and Zenodo record among them is measured, and a Zenodo or Hugging Face DOI is followed to the record it names. The catalogue currently has 37 of 89 projects with such links: 32 GitHub repositories, 35 Hugging Face models, datasets or spaces and 5 Zenodo records. 11 more projects link only to pages we do not measure yet: Kaggle, Harvard Dataverse, figshare, GitLab and organisation pages on Hugging Face or GitHub.

Definitions and thresholds

  • "In the last 12 months" means the 365 days up to and including the day of measurement.
  • The absence factor is the smallest number of people who made at least 50% of all commits, over the whole history.
  • "Outside" means anyone GitHub does not list as the repository's owner, a member of its organisation or a collaborator.
  • Accounts marked as bots, and automation accounts we know of, are left out of every count of people, of the issues and pull requests behind response time and closure, and of the last change on GitHub (CHAOSS Bot Activity). Platform totals such as stars and downloads, and the last update of a Hugging Face model, dataset or space, include their activity.
  • Response time needs at least 5 outside issues and pull requests in the last 12 months, and pull request closure at least 5 outside pull requests, pooled across a project's repositories. An unanswered item counts its age as a lower bound, so a median can read "more than".
  • A date after the day of measurement comes from a wrong clock: it never becomes the last change or the latest release, though such a release still counts in the total.
  • The catalogue's status filter calls a project recently updated when something changed in the last 365 days, and shows no recent updates after 547 days (about 18 months) or when every repository is archived. Zenodo and Harvard Dataverse records count as a stable archive: frozen on purpose, and citable.

What we cannot see

  • Work outside a repository: meetups, data collection, training, and the shared spreadsheet behind this catalogue.
  • Private or gated content, and branches other than the default one.
  • Co-authors named only in a commit message; one person with two accounts or addresses counts twice.
  • Automation accounts we do not know about, and downloads by automated systems, which the platforms count like any other.
  • Members of an organisation who keep their membership private appear as outside contributors.
  • Which commits a fork made itself: its counts include its original repository's history, and the panel says so.
  • Licences stated only in prose: licence detection is mechanical.
  • Hosts we do not measure yet, such as GitLab, Kaggle, Harvard Dataverse and figshare.

How to read it

These are facts, measured the same way for every project, not scores. CHAOSS advises to "avoid using metrics to compare projects against each other when possible" (practitioner guide) and notes that "informational repositories might not have any releases at all" (Starter Project Health).

A dataset that no longer changes can be complete: a project "might seem to be abandoned when it has simply stabilized and might still be widely used" (CHAOSS on sunsetting). Many research repositories are kept by one person, and an absence factor of 1 describes that rather than judging it. "Not measurable" means there was not enough data, not that something is wrong.

The Insights page compares SDGs, never projects, and prints upkeep figures only for a goal with at least 5 measured projects.

The catalogue's default order does use these facts. It sorts projects by how fully they are documented, a score of up to 100 points, and adds up to 40 points for activity: how recently a project changed (a project with a Zenodo or Harvard Dataverse record gets a fixed value instead) and its GitHub stars or Hugging Face downloads in the last 30 days. A very active project can therefore come before a better-documented but quieter one. A project none of whose links responded at the last check loses 20 points, and a project without these facts gets no boost. The facts never decide whether a project is listed.

Privacy

We read only public data through public APIs and publish counts and dates, never the names, usernames or email addresses of contributors. Account names are used during a run only to count each person once, and are not stored. Private repositories are skipped even when they could be read, and a fork's original repository is named only when an organisation owns it.

When it runs

The check runs every Monday at 09:00 UTC. When a source cannot be read during a run, the project keeps its previous measurement for up to 28 days, as long as it covers the same links, and the panel shows the date it was taken. Otherwise the panel names what could not be read.

Corrections and opting out

If a number looks wrong, or you maintain a project and would rather it did not show these facts, open an issue on GitHub or write to jonas.nothnagel@gmail.com. We will correct it or leave the project out; its links are still checked.
